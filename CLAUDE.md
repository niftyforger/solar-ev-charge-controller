# Solar EV Charge Controller

See [README.md](README.md) for a project overview and architecture diagram. This file is the dense technical reference.

## Goal

Divert surplus solar into EV charging by dynamically limiting the charge current an existing "dumb" EVSE offers to the car, based on real-time solar export data from a Sungrow hybrid inverter.

## Control mechanism

- EVSE is single-phase, 230V, up to 32A (7kW class). No usable local API/Modbus/WiFi control path — treated as fixed, unmodifiable hardware.
- The only control point is the **Control Pilot (CP) line**: a ~1kHz PWM signal (IEC 61851-1) whose duty cycle tells the car its max allowed current. The car self-limits based on this signal.
- Approach: intercept the CP wire between the EVSE's internal controller and the vehicle connector, and **actively clamp the line low** partway through each high pulse to shorten it to a lower duty cycle than the charger natively offers, when solar surplus is less than what the charger would otherwise allow. This is a clip, not a regenerate — see "CP interception circuit" below. Only ever clip current down, never lengthen the pulse beyond what the charger sends; the clamp topology makes lengthening physically impossible, not just software-disallowed.
- Duty cycle → current mapping (IEC 61851-1 / SAE J1772 §6.4): `current_A = duty_% x 0.6`, e.g. 10% = 6A (minimum), 26.7% = 16A, 53.3% = 32A. Valid range is ~10%-96% duty.
- **0% duty (or any duty <10%, excluding the reserved 5% digital-comms marker) is NOT a valid "0A" signal** — it's undefined behaviour per spec and some vehicles may fault on it rather than gracefully idle. The clamp must never be used to try to drive below the 10% floor.
- Core 1's CP task implements this as an explicit two-state model — `OSCILLATING` (clamp active per current surplus) vs `STANDBY` (CP disconnect relay open, vehicle isolated from the EVSE) — rather than letting the duty-cycle calculation silently produce an out-of-range value when surplus drops below the 6A floor.
- **What `STANDBY` does electrically:** the clamp can only shunt the line *toward* PE — it has no way to source a positive voltage — so it cannot itself produce a steady-DC "connected, standby" level, and driving it to try to fake one (a near-0% duty) is exactly the undefined/unsafe signal called out above. There's no CP *duty cycle* that means "stop charging" that the clamp alone can safely produce. So when computed surplus can't even support the 6A floor, `STANDBY` instead opens a series relay on the vehicle-side of `CP_LINE` (see "CP interception circuit" below): this removes the vehicle's CP termination from the EVSE's view entirely, which the EVSE reads as a real unplug (state A) and reacts to using its own normal, well-supported disconnect handling — not a signal we're inventing. This replaced an earlier version that released the clamp to native pass-through instead, handing the vehicle full uncapped current at exactly the moment surplus was lowest — the opposite of the intended fail-safe direction (bug caught on the bench 2026-08-31, see "Resolved" below). `MODE_BYPASS` (stale/unavailable data) still releases the clamp to native pass-through and explicitly does **not** open the relay — a data fault should never be treated as confidently "no surplus"; see the fail-safes below.

## State detection & protocol integrity

- The EVSE determines connector state (A/B/C/D) from the DC voltage level of the CP line, and separately verifies the vehicle is genuinely present via a diode-check on the **negative** half-cycle (a real vehicle's CP diode only permits current on the positive half; a missing/reversed diode indicates a fault). Both mechanisms depend on signal features our circuit must not disturb.
- Design requirement: the clamp only ever pulls the line low, only during the **positive (high) portion** of a cycle the EVSE is already driving, and only once oscillation is already established (i.e., mid-charge, state C). It never touches the negative half-cycle, and it never asserts during the A/B handshake or in `STANDBY`. This is guaranteed by the clamp topology itself (see below), not by separate software gating — there's no code path that can clamp when it shouldn't, because the clamp driver is only ever scheduled relative to a rising edge the EVSE itself produced.

## Solar data source

- Inverter: Sungrow SH8.0RS. Meter: DTSU666-20, wired via RS485 directly to the inverter as its smart meter.
- **Do not poll the DTSU666 directly** — it's already a Modbus RTU slave to the inverter, and RTU only supports one master per bus. Read meter/PV data back out of the **SH8.0RS's own Modbus TCP interface** instead (via WiNet-S dongle on the LAN, port 502).
- Installation is single-phase throughout (house + EVSE both single-phase), so total active power at the meter is sufficient — no need to reconcile per-phase figures.
- Useful registers (community-documented, e.g. `mkaiser/Sungrow-SHx-Inverter-Modbus-Home-Assistant` on GitHub):
  - `13009` — total active power at the meter (grid import/export). This is the primary control input.
  - PV/DC output registers (`5016`, `13033`) if computing surplus as PV output minus house load rather than using meter export directly
- `13009` is a 32-bit signed value spanning registers 13009-13010, S32/FC4/unit ID 1 as assumed, 1W/count. **Confirmed against the real WiNet-S (2026-08-24): word order is low-word-first (little-endian), not the big-endian community convention.** `grid_source_dtsu666.cpp`'s `dtsu666_read_power_w` composes `raw` as `(regs[1] << 16) | regs[0]` to match. If the register mapping is ever revisited, re-verify by logging `regs[0]`/`regs[1]` raw and sanity-checking against a known real export/import figure.
- **Also confirmed the same bring-up: the register's native sign polarity is positive = exporting / negative = importing — opposite of the community-convention assumption.** `dtsu666_read_power_w` negates `raw` before returning it, so every other consumer (control loop, shared state, the web status page) keeps using the documented `negative = exporting` convention unchanged — only the raw-register parsing step knows about the hardware's true (inverted) polarity. Re-verify by comparing the signed web-UI figure against a known ground-truth condition (e.g. no solar generation ⇒ must be importing), not just magnitude.
- **Control loop is self-referential**: the EV's own draw is part of what `13009` measures, so raising target current will itself reduce measured export on the next poll. The control loop must account for this — bound the per-adjustment step size, and hold a settling period after each change before reacting to the next reading — rather than treating each poll as an independent, instantaneous surplus measurement. This is a stronger requirement than plain smoothing/hysteresis against cloud transients; it's closed-loop feedback with a delay, not just noisy input.
- **The grid-power reading is behind a swappable interface** (`src/grid_data_source.h`'s `GridDataSource`: a name plus a `read_power_w` function pointer), selected at compile time via `ACTIVE_GRID_DATA_SOURCE` in that header. `GRID_SOURCE_DTSU666` (`src/grid_source_dtsu666.cpp`) is the only implementation today and holds everything specific to this meter/inverter pairing (registers, port, unit ID, word-order/polarity handling above) — none of that lives in `config.h`, so swapping to a different meter/inverter later means adding a new `GridDataSource` and repointing the `#define`, not touching the control loop.

## Hardware: single ESP32-S3

Board: Freenove ESP32-S3-WROOM, mounted on the Freenove ESP32-S3 breakout board — its screw-terminal rails (3V3/5V/GND) supply the whole CP interceptor circuit (sense divider, comparators, optocouplers, clamp MOSFET gate drive), not just the ESP32 itself; see "CP interception circuit" below for why that's a shared-ground design rather than a fully isolated one. Its prototyping area is the natural place to build the interceptor. Dual-core split:

- **Core 0**: WiFi + Modbus TCP client polling the SH8.0RS every few seconds; computes target charge current from surplus power. Adjustments are step-size-limited and settle for a period after each change before the next adjustment is applied, to avoid chasing the EV's own draw (see "Solar data source" above) and to avoid hunting on cloud transients. Also owns the BLE config server (see "BLE configuration" below).
- **Core 1** (pinned, high priority): real-time CP interception.
  - Edge *timestamping/triggering* is a plain GPIO `ANYEDGE` interrupt (`esp_timer_get_time()` in the ISR), not RMT RX — RMT RX's ring-buffer/task-wakeup pipeline is built for after-the-fact burst capture, not reacting to the current edge with low latency.
  - The pre-assert delay is scheduled with the legacy hardware timer group API (`driver/timer.h`): a free-running timer (`TIMER_GROUP_0`/`TIMER_0`, 1MHz/1us-per-tick) armed directly from `cp_sense_isr()` (the GPIO rising-edge ISR itself, in interrupt context, zero task hop) via `timer_set_alarm_value()`/`timer_set_alarm()`. When it fires, `assert_timer_isr()` — also true interrupt context via `timer_isr_callback_add()` — calls `rmt_write_items(..., wait_tx_done=false)` to assert the clamp; RMT's `idle_output_en`+`idle_level=LOW` guarantees release even if the task stalls, and the release itself rides the EVSE's own falling edge (line is already low from the source by then, so it never fights the driver).
  - `cp_interceptor_task` only does *planning*, on its own cadence (`CP_NOTIFY_WAIT_MS`): floating-point duty%/timing-offset math using the ISR's last-measured native period/high-time, producing plain integer tick counts (`s_assertOffsetTicks`, `s_holdTicksRmt`, `s_clampEnabled`) that the ISR applies on the next rising edge, via plain Core-1-local `volatile`s (task→ISR written ticks-then-dutyState so the ISR can never see `CP_OSCILLATING` paired with stale params). This is deliberately the only floating point in the whole path — **never in the ISR**: the Xtensa FreeRTOS port saves/restores the FPU coprocessor lazily, per task, on context switch, not guaranteed on arbitrary interrupt entry/exit, so hardware FP inside an ISR risks silently corrupting the interrupted task's in-flight FP state (confirmed via `portmacro.h`'s `coproc_area`, not a runtime Kconfig check — this sdkconfig has no `FPU_IN_ISR`-style option).
  - This design superseded three earlier approaches (all bench-tested 2026-08-24, kept here so they aren't retried): (1) encoding the pre-assert delay in the RMT item's first segment — re-arming `rmt_write_items()` every ~1ms made that segment's timing land far short of programmed with significant jitter, so only the hold-duration segment depends on RMT timing now; (2) a software `esp_timer` for the delay instead of `driver/timer.h` — worked, but carried real dispatch jitter since `ESP_TIMER_ISR` dispatch isn't available in this build and the esp_timer task isn't core-pinned; (3) routing the clamp decision through `cp_interceptor_task` via a queue (`s_edge_queue`/`EdgeEvent`, since deleted) instead of arming the timer straight from the ISR — ordinary FreeRTOS task-dispatch latency landed on top of the intended offset.
  - **Native duty is learned opportunistically, not measured live while clamping.** Once the clamp is asserting every cycle, the sense point (same tap as the clamp) can't distinguish the EVSE's real falling edge from the clamp's own assert transition — so the falling-edge timestamp only updates the cached native-high-duration on cycles where the clamp did *not* fire (`STANDBY`, `BYPASS`, or `target_duty >= native_duty`). Clamping is skipped entirely until native duty has been learned at least once (fails toward pass-through, never toward a guessed setpoint).
  - Reads a "target amps" value set by Core 0 via a FreeRTOS queue/mutex (not a raw shared variable).
  - Toolchain fact (confirmed by building): `platform = espressif32@6.10.0` resolves to Arduino-ESP32 core 2.0.17 / ESP-IDF 4.4, so RMT means the **legacy** `driver/rmt.h` API (`rmt_config`/`rmt_write_items`/`rmt_item32_t`), not the IDF5 `driver/rmt_tx.h`/`driver/rmt_rx.h` channel API.

### GPIO constraints

- Avoid strapping pins for CP sense/drive lines.
- **Pin assignments (in `include/config.h`, physically confirmed during bench-testing stages 0-2):**
  | Signal | GPIO | Notes |

  | CP PWM sense / EDGE_IN (digital, post-opto) | 5 | `ANYEDGE` GPIO interrupt + timestamping |
  | Clamp drive (RMT TX → opto → MOSFET gate driver) | 6 | |

## BLE configuration

- WiFi SSID/password, the inverter IP, and two independent passwords (one gating BLE config itself, one gating the HTTP control page) have **no compile-time fallback** — `secrets.h` holds only `OTA_PASSWORD`, used solely for OTA flashing (`ArduinoOTA.setPassword()` in `solar_control.cpp`) and nothing else. Everything else is provisioned entirely at runtime over BLE (`src/ble_config.*`), persisted to NVS (`Preferences`, namespace `netcfg`), and read by `solar_control_task`/`require_auth()` out of `shared_state`'s `RuntimeConfig` (see "Firmware implementation" below).
- **Owned by Core 0 only, never Core 1** — same rationale as the LCD it replaced: BLE stack operations are not real-time, and a stuck/disconnected BLE client must never be able to affect the control loop or fail-safes. Uses `NimBLE-Arduino` (much lower RAM/flash footprint than the Arduino core's bundled legacy `BLEDevice.h` stack, and — pinned to the 1.x major version — compatible with this project's `espressif32@6.10.0`/Arduino-ESP32 2.0.17/ESP-IDF 4.4 toolchain; NimBLE-Arduino 2.x targets the newer IDF5-based core, which would conflict with the legacy `driver/rmt.h` API Core 1's CP task depends on — see "Hardware: single ESP32-S3" above).
- **`ble_config_init()`** runs once from `setup()`, independent of WiFi/`solar_control_task` state, so BLE comes up even on a fully unprovisioned board. NimBLE runs its own internal host task; a separate lightweight `ble_periodic_task` (Core 0, `TASK_PRIO_BLE`) re-evaluates the advertising window every ~1s.
- **Transport: Nordic UART Service (NUS), not a custom multi-characteristic GATT profile.** A raw GATT service with several typed characteristics (the original design) requires a GATT-browser app like nRF Connect to drive it field-by-field — it doesn't work with ordinary BLE serial-terminal apps (Serial Bluetooth Terminal, etc.), which auto-detect a small set of known "UART" service profiles and otherwise can't offer a terminal view (this was caught bench-side: a real "connection failed" symptom against Serial Bluetooth Terminal). NUS's UUIDs (`6E400001`/`6E400002`/`6E400003-B5A3-F393-E0A9-E50E24DCCA9E` for service/RX/TX) are the de facto standard those apps recognize, so `ble_config.cpp` exposes exactly that: one RX characteristic (`WRITE | WRITE_NR`) and one TX characteristic (`NOTIFY`), and speaks a small newline-delimited text command protocol over them. `NimBLEDevice::setMTU(247)` is requested up front so multi-line replies don't risk truncating against the default 23-byte ATT MTU before negotiation completes.
- **Command protocol** (`RxCallbacks::onWrite` in `src/ble_config.cpp` assembles incoming bytes into lines on `\n`, tolerating a trailing `\r`, then dispatches via `process_line()`). Property-style commands use `SET <FIELD> <value>` / `GET <FIELD>` prefixes rather than one bespoke verb per field, and each password field is named for what it gates (`WIFI_PASS`/`BLE_PASS`/`WEB_PASS`) rather than a single ambiguous `PASS`:
  | Command | Auth required | Behavior |
  |---|---|---|
  | `AUTH <password>` | no | Compares to `RuntimeConfig.ble_password` — a dedicated BLE-config password, entirely independent of `OTA_PASSWORD` and of the web-control-page password below. If it has never been set (empty, factory-fresh device), `AUTH` authenticates unconditionally — the same "wide open until first provisioned" bootstrap this project already uses for WiFi, since there is otherwise no way to set that first password at all. Sets/clears a global authenticated flag (single-operator bench device, not multi-tenant — reset on every new connection) that gates every `SET`/`COMMIT` command below. Replies `OK` / `ERR bad password`. |
  | `SET WIFI_SSID <ssid>` | yes | Stages a new SSID (not yet persisted/applied). Replies `OK` / `ERR not authenticated` / `ERR invalid ssid`. |
  | `SET WIFI_PASS <password>` | yes | Stages a new WiFi password. Same reply pattern. |
  | `SET INVERTER_IP <ip>` | yes | Stages a new inverter IP; anything that doesn't parse via `IPAddress::fromString()` is rejected outright, leaving the previous staged value in place. |
  | `COMMIT` | yes | The one atomic "apply" step for the three staged WiFi/inverter fields: persists them to NVS and publishes them into `shared_state`'s `RuntimeConfig` together via `shared_state_set_wifi_config()` (bumping `generation`), so `solar_control_task` never observes a half-updated config (e.g. a new SSID paired with the old password) even if a client sent fields one at a time first. |
  | `SET BLE_PASS <password>` | yes | Sets the password `AUTH` will require on future connections. Applies immediately (own NVS write + `shared_state_set_ble_password()`) rather than going through `COMMIT` — it's independent of the WiFi fields, not part of that atomic group, and does not bump `generation`. |
  | `SET WEB_PASS <password>` | yes | Sets the HTTP control-page password (see "OTA & simulation mode" below). Same immediate-apply pattern as `SET BLE_PASS`. |
  | `GET STATUS` | no | Reports the current SSID (not secret), staged inverter IP, live device IP (`WiFi.localIP()`, or `"0.0.0.0"` when not connected — the one piece of information BLE config exists partly to expose now that there's no LCD to show it on), provisioned/auth flags, and whether `BLE_PASS`/`WEB_PASS` have ever been set (`blepass_set`/`webpass_set`). **Deliberately never echoes any password** — with everything flowing through one RX/TX pipe instead of per-field GATT characteristics, there's no GATT-permission-level guarantee against reading one back (the original design's `WIFI_PASSWORD` characteristic had no READ property at all); not sending any password back in any reply is what enforces that now, so this omission in `handle_status()` is deliberate, not incidental. |
  | `HELP` | no | Lists the commands above. |
  | `SET`/`GET` with an unrecognized field | — | `ERR unknown field, try HELP` |
  | anything unrecognized | — | `ERR unknown command, try HELP` |
- **Advertising window**: BLE advertises for `BLE_ADVERTISE_WINDOW_MS` after each boot — **except** while the device has never been provisioned (no SSID ever committed to NVS), in which case it advertises indefinitely, since BLE is the only way to configure WiFi at all and a time limit there could strand a factory-fresh board out of range of its one configuration path. Re-evaluated every ~1s by `ble_periodic_task`; stopping advertising doesn't drop an already-open connection, so a client mid-provisioning inside the window is never cut off.
- **Core 0 apply flow** (`solar_control.cpp`): `connect_wifi()` reads SSID/password out of `RuntimeConfig` and deliberately does not call `WiFi.begin()` at all if unprovisioned/empty — retried on the normal `WIFI_RECONNECT_INTERVAL_MS` cadence. `solar_control_task` tracks the last-applied `generation` and, on a change, disconnects (if connected), re-parses the inverter IP, and lets the existing reconnect branch pick up the new credentials. `generation` only ever changes via `shared_state_set_wifi_config()` (i.e. `COMMIT`) — `SET BLE_PASS`/`SET WEB_PASS` never trigger a WiFi bounce, since neither is a reason for Core 0 to reconnect. Being unprovisioned or WiFi-less is already safe without any new logic: Core 1's existing stale-data fail-safe (`MODE_BYPASS` after `STALE_DATA_TIMEOUT_MS`) already treats "no working network/data path" as native CP pass-through, never a guessed setpoint or a disconnect.

## CP interception circuit

See `schematic/schematic.png` (source: `schematic/solar-ev-charge-controller/`) for the actual schematic — this section is the rationale behind it, not a restatement of every value; component references below (`R5`, `U2`, `Q2`, etc.) match that drawing. **Reference designators were renumbered by a KiCad annotation pass after this section was first written; the designators below reflect the current schematic, wire-traced pin-by-pin to confirm — see the git history around 2026-09-02 if reconciling against an older revision of this doc.**

- **Reference**: CP (and PP) are referenced to PE (Protective Earth), not to a floating signal ground or neutral. Confirm continuity from the connector's PE pin to the CP circuitry's reference before tapping in.
- **Isolation is signal-only, not power-domain**: the three digital lines that cross into/out of the ESP32's logic domain (`EDGE_IN`, `CONNECTED_IN`, `CLAMP_DRIVE`) each go through their own optocoupler (`U3`/`U4`/`U1` respectively, SFH617A-3). The sense divider, both comparators, and the clamp MOSFET (`Q2`) share one `GND`/`+5V` with the ESP32 side — there is no separate PE-only supply rail. Protection against a CP-side fault or wiring mistake reaching the ESP32 comes from the high-Z sense divider (100kΩ `R5` in series) and the `D3`/`D4` clamp diodes to `+5V`/`GND`, not from full galvanic isolation. (Accepted deliberately: this is a real reduction from an earlier fully-isolated design — see [Open questions](#open-questions-for-implementation) if that's ever revisited.)
- **Sensing**: resistor divider (`R5` 100k / `R6` 33k) brings the +/-12V CP swing down to a single `SENSE` node, compared by an LM393 dual comparator (`U2`) against two fixed references off a resistor ladder (`R8`/`R9`/`R10`): REF_CONN ≈2.5V on comparator unit 1 → pulled up to `+5V` by `R11`, drives `U3`'s LED (through `U3` to `+3.3V`-pulled-up `R13`) → `CONNECTED_IN`; REF_EDGE ≈0.45V on comparator unit 2 → pulled up to `+5V` by `R12`, drives `U4`'s LED (through `U4` to `+3.3V`-pulled-up `R14`) → `EDGE_IN`. Each comparator output feeds its own optocoupler into an ESP32 GPIO (`CP_CONNECTED_SENSE_GPIO`, `CP_PWM_SENSE_GPIO`). Two thresholds on one node gives four resolvable buckets, not full six-level A/B/C/D/E/F discrimination: `CONNECTED_IN` alone only splits A (~12V) from everything else; combined with `EDGE_IN`'s toggling (oscillating) and idle level (high vs low), firmware in `read_connector_state()` (`cp_interceptor.cpp`) derives A / B / C(+D) / FAULT(=E+F). C is conflated with D, and E is conflated with F — the amplitude information a window comparator would preserve is discarded by a binary comparator. Accepted tradeoff: D (ventilated charging) is unused on this install, and E/F both already map to "don't clamp" control-wise, so the conflation only costs status/LCD granularity, not safety.
- **Sensing values, hand-verified (2026-08-30)**: traced the actual net topology in `schematic/solar-ev-charge-controller/solar-ev-charge-controller.kicad_sch` rather than assuming it — the `R8`/`R9`/`R10` ladder is fed from the `+5V` rail (confirmed by a `power:+5V` symbol placed directly above `R8`), not `+3.3V`. At nominal values this gives REF_CONN = 5V×(R9+R10)/(R8+R9+R10) = **2.500V exactly** and REF_EDGE = 5V×R10/(R8+R9+R10) = **0.450V exactly**, both landing correctly between their intended CP-state boundaries after the `R5`/`R6` divider (ratio 33k/133k = 0.2481): REF_CONN between state B (9V→2.23V) and A (12V→2.98V); REF_EDGE between state E (0V) and D (3V→0.74V). The on-paper values are correct. However, at rated ±5% resistor tolerance, worst-case REF_CONN (2.375V) can dip *below* worst-case state-B SENSE (2.406V) — a ~31mV overlap risking an A/B misread in the unlucky corner, vs. a comfortable 267mV margin at nominal; REF_EDGE has no such issue (~197mV worst-case margin to state D even at ±5%). `R5`, `R6`, and `R8` are therefore specified at 1% tolerance (`R9`/`R10` stay 5%, their margin is already sufficient) to close that gap — see the `Tolerance` property on those three symbols in the schematic. **Confirmed against the real EVSE in bench-testing stage 2**: thresholds land where expected, `read_connector_state()`'s A/B/C/FAULT bucketing behaves as designed.
- **Clamping (generation)**: not a full waveform regenerator, and not a series break either — the CP wire from the EVSE to the vehicle connector runs continuous and uncut. `Q2` (2N7000, N-channel MOSFET) taps onto that wire through a series blocking diode (`D2`) and shunts it toward `GND` when driven, via the opto-isolated `CLAMP_DRIVE` line from Core 1, only during the high portion of a cycle already in progress, per the RMT-scheduled assert/release described above. `D2` keeps the negative half-cycle (and `Q2`'s own body diode) from interacting with the tap. At all other times (negative half-cycle, STANDBY, A/B handshake) `Q2` is off and the EVSE's native signal passes through completely untouched.
- **`Q2`'s gate defaults off, not relay-gated**: `R3` (10k) pulls `Q2`'s gate to `GND` (through the same node as `R4`, the opto output's 220Ω gate series resistor) whenever the `CLAMP_DRIVE` optocoupler (`U1`, LED driven from `CLAMP_DRIVE_GPIO` through its own 220Ω series resistor `R7`) isn't actively driving it. There is no relay in *this* leg — an earlier revision used one (`K1`, gating the MOSFET's drain for a "physically disconnected, not just failed-safe" guarantee); it's gone from the current schematic and was never actually drawn into it. (Not to be confused with the *new* disconnect relay described below, which serves a different purpose — actually breaking `CP_LINE` to the vehicle, not gating the clamp leg — and reuses the `K1` reference designator and its originally-intended GPIO for an unrelated function.) The pull-down is a weaker guarantee than the old `K1` concept was: a shorted `Q2` (drain-source) or a shorted opto secondary can still pull `CP_LINE` low continuously with no way to interrupt it. The failure mode itself is still non-hazardous (see below): it reads as a fault/disconnect to the EVSE.
- **Disconnect relay (`K1`)**: a normally-closed (NC), energize-to-open relay in series on `CP_LINE`, spliced in **downstream of the `R5`/`D2` sense-and-clamp tap, between that tap and the vehicle connector** — the tap itself doesn't move. Coil driven by its own optocoupler and a low-side driver transistor (`Q1`, 2N7000), with a flyback diode (`D1`) across the coil. De-energized (no drive — ESP32 unpowered, firmware not yet initialized, watchdog reset) is the NC/closed state: `CP_LINE` passes through to the vehicle unconditionally, same fail-safe direction as `R3`/`Q2`. Only Core 1 actively energizing it (see `CP_STANDBY` above) opens it. With the relay open, the vehicle's own CP diode/resistor network is isolated from the EVSE entirely — the EVSE's own controller, sensing the same node further upstream, sees CP with no vehicle load at all, electrically indistinguishable from a real unplug (state A), and stops offering charge via its own normal handling. Reclosing the relay reconnects the vehicle's termination and both the EVSE and this board's own `CONNECTED_IN` sense renegotiate the handshake (A→B→C) exactly as on a fresh plug-in. **Confirmed clean twice**: a manual CP-wire disconnect while charging (2026-08-31) stopped and resumed charging with no fault and no manual intervention on either side (see "Resolved" in Open Questions below); the actual `K1` relay circuit (opto drive, driver transistor, contact timing) was then bench-validated the same way in stages 1-2 — opens/closes cleanly, no chatter.
- **Inherent fail-safe properties**:
  - No drive on `CLAMP_DRIVE` (idle, ESP32 unpowered, firmware not yet initialized, or watchdog-triggered restart) → `R3` holds `Q2`'s gate low → CP passes through at the EVSE's native (uncapped) duty cycle unconditionally. Non-hazardous: charging continues at whatever the EVSE would natively allow, just without solar-following.
  - `Q2` (or its drive path) stuck on/shorted → CP line held low → EVSE reads this as a state fault or vehicle disconnect and stops offering charge. Non-hazardous: charging stops rather than misbehaving.
  - Because the clamp can only pull the line toward `GND`, it cannot physically raise the effective duty cycle above native, regardless of firmware state.
  - No drive on the disconnect relay's coil (idle, unpowered, firmware not yet initialized, or watchdog reset) → NC contact stays closed → `CP_LINE` passes through to the vehicle unconditionally, same as the clamp's own power-loss case. Losing the ESP32 must never leave the vehicle unable to charge at all.
- **Explicit fail-safes**:
  - Stale-data timeout: if Core 0 hasn't successfully polled the inverter within ~60s, Core 1 sets `s_mode = MODE_BYPASS`, which stops `cp_sense_isr()` from ever scheduling a clamp assertion **and** keeps the disconnect relay closed regardless of the current duty-state — the EVSE's native signal passes through unmodified, the same end state as the power-loss case below. (Accepted tradeoff: a fault in the data path means charging proceeds at the EVSE's native/uncapped rate, potentially from grid, until the fault clears — deliberately chosen over pausing charging or guessing a setpoint. A data fault is never treated as a confident "no surplus" decision, so it never triggers a disconnect.)
  - Hardware watchdog timer on the CP task, so a firmware hang forces reboot rather than freezing mid-cycle; `CLAMP_DRIVE`'s RMT output defaults to idle-low on reset (`idle_output_en` + `idle_level=LOW`), not requiring an explicit "off" command.
  - Power-loss bypass: if the ESP32 loses power/crashes, `CLAMP_DRIVE`'s optocoupler simply stops being driven, `R3` holds `Q2`'s gate low, the disconnect relay's optocoupler simply stops being driven so its coil de-energizes to NC/closed, and the EVSE's original unmodified CP signal was never at risk of interruption in the first place.
  - Relay dwell-time debounce (`RELAY_MIN_DWELL_MS`): the `CP_OSCILLATING`/`CP_STANDBY` duty state (and therefore the relay) can't flip again until a minimum time has elapsed since its last change, on top of the existing amps hysteresis — bounds relay cycle count and gives the EVSE/vehicle time to complete a full unplug/replug handshake before another one can be triggered.

## Firmware implementation

PlatformIO project, `env:freenove_esp32_s3_wroom`, framework `arduino`. Builds clean as of this writing (`pio run`, zero warnings). Layout:

- `include/config.h` — pins, control-loop constants, thresholds. Anything still marked TBD/placeholder here corresponds 1:1 to an item in "Open questions" below.
- `include/secrets.h` (gitignored) — just `OTA_PASSWORD`, used solely for OTA flashing. **Auto-generated before every build** from `OTA_PASSWORD` in `.env` (gitignored, template `.env.example`) by `tools/sync_secrets.py`, wired in as a PlatformIO pre-build step (`extra_scripts = pre:` in `platformio.ini`'s `[env]`, so it runs for every env and invocation path, including the VSCode PlatformIO IDE buttons) — don't edit `secrets.h` by hand, edit `.env` instead. This keeps `OTA_PASSWORD` in exactly one place rather than two gitignored files that previously had to be kept in sync manually. `[env:ota]`'s upload step (the `--auth`/`upload_port` espota flags) is a separate mechanism reading the same `.env` file but can't go through a pre-build script at all — a build's `extra_scripts` runs in a child process, so anything it sets in `os.environ` never reaches the parent `pio` process that performs the actual upload (confirmed by testing) — so `[env:ota]` declares no `upload_port`/`upload_flags` in `platformio.ini` and instead relies on PlatformIO's own built-in `PLATFORMIO_UPLOAD_PORT`/`PLATFORMIO_UPLOAD_FLAGS` env vars, which every `pio` invocation reads regardless of launch path. Two ways to populate those from `.env`: `tools/ota_upload.py` sets them for one CLI invocation; `tools/sync_env_vars.py` persists them as Windows user environment variables (one-time, requires a VSCode restart afterward) so the PlatformIO IDE's own "Upload" button works directly — see the `[env:ota]` comment in `platformio.ini`. WiFi credentials, the inverter IP, and the BLE-config/control-page passwords are not compiled in at all — see "BLE configuration" above.
- `src/shared_state.*` — the Core0↔Core1 bridge: an `xQueueOverwrite` queue (length 1) for the target-amps command, plus a mutex-protected status struct in each direction. Core 1's side always uses zero-timeout mutex/queue takes so a contended mutex can never stall the real-time task. Also holds the BLE-provisioned `RuntimeConfig` (WiFi SSID/password, inverter IP, `generation` counter, BLE-config password, control-page password) — written by `ble_config.cpp`, read by `solar_control_task`.
- `src/modbus_tcp_client.*` — hand-rolled minimal Modbus TCP client (no external lib): short-lived connection per poll rather than a held-open socket, since the WiNet-S gateway's concurrent-connection support is unconfirmed. Generic - no knowledge of any specific meter/inverter's register map.
- `src/grid_data_source.h` / `src/grid_source_dtsu666.cpp` — the `GridDataSource` interface and its one implementation (DTSU666 via the SH8.0RS/WiNet-S) - see "Solar data source" above.
- `src/solar_control.*` — Core 0: WiFi connect/reconnect (from `RuntimeConfig`, not compile-time credentials), poll loop, the step-limited/settling-gated control law, OTA, and the sim-mode control page (see below).
- `src/ble_config.*` — Core 0: BLE server provisioning WiFi/inverter-IP config, the BLE-config and control-page passwords, and exposing the device's current IP — see "BLE configuration" above.
- `src/cp_interceptor.*` — Core 1: GPIO-interrupt edge capture, RMT-generated clamp waveform, the disconnect relay drive, the `BYPASS`/`ACTIVE` × `OSCILLATING`/`STANDBY` state machine, task watchdog.

### OTA & simulation mode

- **OTA**: `ArduinoOTA` starts once Core 0's WiFi connects (`solar_control.cpp`), password-protected via `OTA_PASSWORD` (`secrets.h`, auto-generated from `.env` — see "Firmware implementation" above). Lets firmware be reflashed over the LAN once the board is mounted near the EVSE, without pulling it for USB access. Because Core 0 blocks on flash-writing during an actual OTA push, the Modbus/sim poll loop pauses for the duration; if a push runs longer than `STALE_DATA_TIMEOUT_MS` (60s), Core 1's existing stale-data fail-safe engages and bypasses to native pass-through mid-update — expected behavior, not a fault to avoid.
- **Simulation mode**: for bench/night-time development when there's no real solar export to test against. A small HTTP control page is served at `http://<device-ip>/` once WiFi is up, letting you toggle between Real (actual Modbus reads) and Simulated (a value you set from the page) and adjust the simulated watts live. Authentication is HTTP Basic Auth, username `admin`, password `RuntimeConfig.web_password` — set entirely over BLE via `SET WEB_PASS` (see "BLE configuration" above), **never** `OTA_PASSWORD`. Until a control-page password has been committed at least once, `require_auth()` (`solar_control.cpp`) refuses every request outright (HTTP 403 pointing at `SET WEB_PASS`) rather than falling back to an empty or guessable credential — unlike WiFi provisioning, there's no "open until first set" grace period here, by deliberate choice. This is otherwise a runtime, network-reachable toggle rather than a physical jumper — accepted deliberately, since the CP interceptor's hardware topology already bounds what bad/malicious simulated data can do (it can only ever clip current down or fall back to native pass-through, never raise it above the EVSE's native offer — see "Inherent fail-safe properties" above). Backed by `SolarStatus.simulated`. Stale-data fail-safe testing still requires real hardware (stage 3 below) — sim mode keeps `last_poll_success_ms` advancing on its own, so it doesn't exercise that path.

Bench-tested through stage 2 of the plan below (CP simulator alone, then real EVSE + CP simulator) — stage 3 (real EVSE + real vehicle) is next.

## Bench testing & validation plan

Stage the hardware bring-up so the real EVSE and vehicle are never the first thing exercising a new circuit revision. Stages 0-2 are complete and passed clean; stage 3 (real vehicle) is next.

0. **BLE provisioning, before any of the CP stages below — done.** WiFi and the inverter IP have no compile-time fallback, so a fresh board can't reach real solar data at all until this is done once. Procedure: erase NVS (or flash fresh), confirm BLE advertises indefinitely while unprovisioned, connect with a BLE serial-terminal app (auto-detects the Nordic UART Service, no manual characteristic selection) and confirm `HELP`'s command list; confirm `SET`/`COMMIT` commands reject with `ERR not authenticated` before `AUTH` and accept after; confirm `GET STATUS` reports `device_ip=0.0.0.0` before WiFi connects and the real IP after, and never echoes a password; set `BLE_PASS`/`WEB_PASS`, reconnect, and confirm `AUTH` now requires the exact password; confirm the HTTP control page 403s with no prompt before `WEB_PASS` is set and works with Basic Auth after; confirm advertising stops `BLE_ADVERTISE_WINDOW_MS` after boot once provisioned; confirm OTA still authenticates against `OTA_PASSWORD` independent of all of the above.
1. **CP simulator, no EVSE/vehicle involved — done.** Bench CP simulator: an oscillator standing in for the EVSE's native PWM, plus a switchable diode/resistor network standing in for the vehicle's state-dependent CP termination (A/B/C, with and without the state-detection diode). Validated sensing accuracy, clamp timing (assert point vs. target duty, release point vs. native falling edge), that the negative half-cycle and STANDBY/handshake periods are never touched, and that the disconnect relay opens/closes cleanly.
2. **Real EVSE + CP simulator standing in for the vehicle — done.** Confirms the circuit against the EVSE's actual timing/tolerances without a vehicle attached, and that its state machine and diode check still function through the interceptor. Comparator thresholds (REF_CONN/REF_EDGE) landed where expected; relay open/close mid-simulated-charge was treated as a normal unplug/replug — no fault code, no manual intervention, current resumed ramping normally on reconnect.
3. **Real EVSE + real vehicle, supervised — next.** Start with conservative (small) clipping targets, confirm the car actually reduces draw accordingly, watch for any fault/disconnect behavior, and only then test larger clip ranges. Deliberately trigger the stale-data and power-loss fail-safes (kill WiFi, pull ESP32 power) while charging is active and confirm the bypass actually engages, before ever leaving the system unattended. Repeat the relay open/close test from stage 2 against the real vehicle, and check relay cycling rate against `RELAY_MIN_DWELL_MS` under real, noisy surplus readings to confirm it doesn't chatter. This is also what answers the open question below on whether the vehicle accepts live duty-cycle changes mid-charge.

## Open questions for implementation

Still genuinely unresolved (no amount of firmware work settles these — need the real vehicle, or a design-philosophy call):

- Whether this specific vehicle accepts live CP duty-cycle changes while charging is in progress, or requires a brief state transition (e.g. a State B blip) before it'll honor a new lower current — the next thing to determine, in bench-testing stage 3. This affects how aggressively the control loop can adjust and whether an adjustment needs to be wrapped in a deliberate pause/resume.
- Whether the shared-ground/signal-only-isolation design (see "CP interception circuit" above) is acceptable long-term, or whether a fully galvanically-isolated PE-side supply is worth adding back later.

Have an implemented default now, but still need bench confirmation/tuning:

- Step-size (`STEP_MAX_A_PER_POLL`), settling-period (`SETTLE_MS`), and hysteresis-band (`HYSTERESIS_A`) values for the control loop — placeholders in `config.h`, tune once real solar/EV behavior is observed (stage 3).
- Disconnect-relay dwell time (`RELAY_MIN_DWELL_MS`) — functional open/close behavior (no chatter) confirmed against the real EVSE in stage 2; the numeric value itself still awaits real vehicle unplug/replug handshake timing (stage 3).
- Clamp trigger-dispatch-latency compensation (`CLAMP_DISPATCH_LATENCY_US`) — placeholder, characterize with a scope against real hardware (not just the bench simulator). Covers the full ISR→hardware-timer→RMT dispatch path (see Core 1 above), not just the RMT trigger.

Resolved, kept here for the record:

- **BLE range/reliability inside the (metal) EVSE enclosure — confirmed adequate.** No external antenna or "open the enclosure to provision" workflow needed.
- **Resistor divider/comparator thresholds (REF_CONN ≈2.5V, REF_EDGE ≈0.45V) — confirmed landing where expected against the real EVSE in bench-testing stage 2.** `read_connector_state()`'s A/B/C/FAULT bucketing behaves as designed; the 1% tolerance on `R5`/`R6`/`R8` (see "Sensing values, hand-verified" above) is sufficient.
- **GPIO pin assignments — physically wired and confirmed correct during bench-testing stages 0-2.** See the pin table above and `config.h`.
- **Relay-based CP disconnect/reconnect is clean and gracefully recoverable.** Confirmed twice: a manual CP-wire disconnect while charging (2026-08-31) stopped and resumed charging cleanly with no fault and no manual intervention on either side; the actual `K1` relay circuit (opto drive, driver transistor, contact timing) was then bench-validated the same way in stages 1-2 — opens/closes cleanly, no chatter. This was the core assumption behind the `CP_STANDBY` fix below, and confirms the relay-based disconnect approach is sound both electrically and in the built circuit.
- **Both CP sense GPIOs' idle-level polarity, bench-confirmed 2026-08-30, inverted from the original "HIGH = above threshold" assumption.** `CP_CONNECTED_SENSE_GPIO` reads LOW for state A and HIGH when connected; `CP_PWM_SENSE_GPIO` reads LOW while the real CP line is high and HIGH while low — `read_connector_state()`/`cp_sense_isr()` updated accordingly. The `CP_PWM_SENSE_GPIO` inversion caused a clamp-timing fault: `cp_sense_isr()` was arming the clamp timer off what it read as a rising edge but was actually the real falling edge, so the clamp asserted a duty%-proportional delay *after* the line's real fall — clamping into the negative half-cycle, which must never happen. Reproducible and quantified (10% duty → ~128µs after the real fall, growing with duty%) before the fix.
- A related bug fixed the same day: the clamp hold-duration formula in `cp_interceptor_task()` computed `holdUs` from the already-latency-compensated assert offset instead of the true target assert instant, double-counting `CLAMP_DISPATCH_LATENCY_US`. Fixed by deriving `holdUs` from the uncompensated target instant instead.
- **`CP_STANDBY` released the clamp to full native pass-through instead of stopping charging, bug caught on the bench 2026-08-31.** As target duty decreased past the ~6A/10%-duty floor, the old behavior released the clamp entirely, handing the vehicle the EVSE's uncapped native current (16-32A) at exactly the moment solar surplus was lowest — backwards from the project's goal. Root cause: the amps-based `OSCILLATING`/`STANDBY` hysteresis independently overrode the duty-cycle floor already enforced by `constrain(..., CP_MIN_DUTY_PCT, ...)`, and its fallback (full native pass-through) was carried over from the stale-data bypass case without noticing "no surplus" and "don't know" call for opposite responses. Fixed by adding the disconnect relay: `CP_STANDBY` while `MODE_ACTIVE` now opens it instead of releasing the clamp; `MODE_BYPASS` is unaffected and still releases to native pass-through.
