# Solar EV Charge Controller

See [README.md](README.md) for a project overview and architecture diagram. This file is the dense technical reference.

## Goal

Divert surplus solar into EV charging by dynamically limiting the charge current an existing "dumb" EVSE offers to the car, based on real-time solar export data from a Sungrow hybrid inverter.

## Control mechanism

- EVSE: single-phase 230V, up to 32A (7kW). No API/Modbus/WiFi control path — treated as fixed hardware.
- Only control point: the **Control Pilot (CP) line**, a ~1kHz PWM signal (IEC 61851-1) whose duty cycle sets the car's max current. `current_A = duty_% × 0.6` (10% = 6A min, 26.7% = 16A, 53.3% = 32A; valid range ~10-96% duty).
- Approach: clamp the CP line low partway through each high pulse, between the EVSE's controller and the vehicle connector, shortening duty below native when surplus is less than the charger would otherwise allow. A clip, not a regenerate — see "CP interception circuit". The topology makes lengthening the pulse physically impossible, so it can only ever clip down, never above native.
- **Duty <10% (excluding the reserved 5% comms marker) is not a valid "0A" signal** — undefined per spec, may fault some vehicles. Never drive below the 10% floor.
- Core 1 models this as `OSCILLATING` (clamp active per surplus) vs `STANDBY` (CP disconnect relay open, vehicle isolated), rather than letting the duty calculation go out-of-range below the 6A floor.
- `STANDBY`: the clamp can only shunt toward PE, never source voltage, so it can't hold a steady "connected, standby" level — attempting that would itself be the undefined signal above. So below-floor surplus opens a series relay on the vehicle side of `CP_LINE` instead, which the EVSE reads as a real unplug (state A) and handles via its own normal disconnect path (the earlier alternative — releasing to full native pass-through here — is in "Resolved" below). `MODE_BYPASS` (stale/unavailable data) still releases to native pass-through without opening the relay — a data fault is never treated as confident "no surplus."

## State detection & protocol integrity

- The EVSE determines connector state (A/B/C/D) from the CP line's DC voltage level, and separately verifies the vehicle via a diode-check on the **negative** half-cycle (a real CP diode only permits current on the positive half). Both depend on signal features our circuit must not disturb.
- The clamp only ever pulls the line low, only during the **high** portion of a cycle the EVSE is already driving, only once oscillating (state C) — guaranteed by topology (scheduled off the EVSE's own rising edge, not software gating). It never touches the negative half-cycle, the A/B handshake, or `STANDBY`.

## Solar data source

- Inverter: Sungrow SH8.0RS. Meter: DTSU666-20 via RS485 to the inverter (its Modbus RTU slave) — **don't poll it directly** (RTU is one-master-per-bus); read power/PV data via the inverter's own **Modbus TCP** interface instead (WiNet-S dongle, LAN port 502).
- Single-phase throughout (house + EVSE) — total active power at the meter is sufficient, no per-phase reconciliation needed.
- Registers (community-documented, e.g. `mkaiser/Sungrow-SHx-Inverter-Modbus-Home-Assistant`):
  - `13009` — total active power at the meter (grid import/export), S32/FC4/unit 1, 1W/count, spans regs 13009-13010. Primary control input. **Confirmed on the real WiNet-S (2026-08-24): word order is low-word-first** (`raw = (regs[1]<<16)|regs[0]`, opposite the community big-endian convention) **and native sign is positive=exporting** — `sungrow_winet_read_power_w` negates it so every other consumer sees the documented negative=exporting convention.
  - `5018` — Phase A voltage, U16, ×0.1V. Community-documented; unconfirmed against this specific hardware.
  - `13021` — battery power **magnitude**, a standalone single register (not the low half of a `13021`-`13022` S32 pair — that assumption produced a garbage 58M W reading, see "Resolved"). **It carries no direction: it reads positive while charging and positive while discharging alike**, so no sign convention applied to this register alone can be right in both directions — which is exactly why three separate 2026-09-04/05 attempts to fix it by negating/not-negating each looked correct against whichever direction happened to be observed and wrong against the other (see "Resolved"). Read as an unsigned magnitude via `fabsf()`, which also stays correct on the post-Oct-2024 Sungrow firmware where this register *is* genuinely signed. Defensive ±20kW sanity bound (`SUNGROW_WINET_BATTERY_POWER_SANITY_MAX_W`). Ran ~10% below the Sungrow app's figure during one cloudy correlation window — plausibly just window skew, worth rechecking under steadier conditions.
  - `13000` — **Power Flow Status**, U16 bitfield; the direction source for `13021` above. Bit 1 (`0x0002`) = battery charging, bit 2 (`0x0004`) = battery discharging. (Other bits exist and are unused here: `0x0001` PV generating, `0x0008` positive load power, `0x0010` exporting, `0x0020` importing, `0x0080` negative load power.) `sungrow_winet_read_power_w` requires both this and `13021` to read successfully, and treats *both bits set* — or *neither bit set while `13021` exceeds `SUNGROW_WINET_BATTERY_IDLE_EPSILON_W` (100W)*, the "status register stuck at zero" fault some models show — as an unusable reading that fails `outBatteryDataValid` rather than being guessed at. Neither bit set with a near-zero magnitude is a trustworthy idle 0W. Cross-checked against mkaiser's register notes and evcc's Sungrow template, which derives its sign the same way.
  - `5213`-`5214` — "battery power, wide range", S32, low-word-first, **genuinely signed with negative=charging** (opposite `outBatteryW`, so it would need negating). Present on this inverter and confirmed against the same 2026-09-06 transition capture (+2654W discharging, −1794W charging, magnitudes identical to `13021` throughout); Sungrow's own datasheet recommends it over `13021`. **Unused** — `13021`+`13000` is what got directly confirmed in both directions, needs no new word-order assumption, and works on the models where `5213` returns "illegal data address". Documented as the fallback if `13000` ever proves unreliable. A cross-check between the two was considered and rejected: the reads are milliseconds apart on a value that can swing >600W in 5s, so honest skew would trip spurious `outBatteryDataValid` freezes mid-charge.
  - `13020` — battery current. **Do not use as a direction source**: its sign was observed going negative *during* a discharge in the 2026-09-06 capture while `13000` and `13021` stayed consistent (magnitude tracked fine). evcc uses it as a sign fallback; this hardware doesn't support that.
  - PV/DC output registers (`5016`, `13033`) exist if surplus is ever computed as PV output minus house load instead of meter export.
- **Control loop is self-referential**: the EV's own draw is part of what `13009` measures, so raising target current reduces the next poll's measured export — delayed closed-loop feedback, not just smoothing against cloud transients. This is why the loop needs damping and not merely a settling delay; see "Control-loop damping" below for the stability argument and the blanking/averaging/gain scheme that replaced the old single `SETTLE_MS` window.
- **Grid source is a swappable interface** (`src/grid_data_source.h`'s `GridDataSource`: stable `id`, display `name`, `read_power_w`), selected at runtime from the HTTP control page, not compile-time. `grid_data_source_registry.cpp` lists every compiled-in source (`GRID_SOURCE_REGISTRY[]`, index 0 = `GRID_SOURCE_SUNGROW_WINET` = default/fallback for any unrecognized id). `solar_control.cpp` owns the active selection — a `solar_control_task`-local static (Core 0 only), persisted in its own NVS namespace (`"gridsrc"`, independent of BLE's `"netcfg"`) via `/api/set_source`. `GRID_SOURCE_SUNGROW_WINET` (`grid_source_sungrow_winet.cpp`) holds everything meter/inverter-specific — adding a real second source means adding a new `GridDataSource` and registry entry, nothing else.
- `GridDataSourceReadFn`: `bool(IPAddress host, float currentDrawW, float &outWatts, float &outVoltageV, float &outBatteryW, bool &outBatteryDataValid)`. `currentDrawW` (the wattage currently commanded) feeds simulated sources so they can model the EV's own draw the way a real meter's reading always includes it (real sources ignore it). `outVoltageV`/`outBatteryW` let each source report its own grid voltage and battery power; `outBatteryDataValid` is the trust flag on `outBatteryW` (see below).
- **Home-battery discharge is excluded from EV-charging surplus** (2026-09-04): the meter sits downstream of the home battery, so it can't distinguish fresh-PV export from battery-discharge export — left unhandled, the loop would divert battery power into EV charging. `outBatteryW` (positive=charging, negative=discharging, 0=idle/no battery) lets `solar_control_task()` compute `effectiveGridPowerW = gridPowerW + fmaxf(0, -batteryPowerW)` before calling `compute_next_target_amps()`, which stays a pure function of "surplus" with no battery-specific knowledge. `status.grid_power_w`/the JSON `grid_w` still report the raw meter reading; the exclusion is surfaced separately as `battery_w`/`battery_state`/`surplus_excluded_w`. Algebraically this cancels the battery term exactly, regardless of discharge magnitude, at every poll — `effectiveGridPowerW` always equals the true house+EV-load-minus-PV figure whenever `outBatteryW` is accurate (energy-balance identity: `gridPowerW = houseLoad + evLoad - pv + batteryPowerW` always holds, so adding back `-batteryPowerW` always leaves exactly `houseLoad + evLoad - pv`).
- **`outBatteryDataValid` guards the exclusion above against unmeasured discharge** (2026-09-05): the exclusion is only as good as `outBatteryW`, and `GRID_SOURCE_SUNGROW_WINET`'s battery-register read has no failure path visible to the caller — a failed read or a sanity-bound rejection just falls through to `lastGoodBatteryW` (a `static float` defaulting to `0.0f`), which is indistinguishable from a confirmed-idle battery. That meant a real, ongoing discharge that hadn't yet been successfully *measured* (fresh boot before the first successful battery read, a misread, or a rejected reading) wasn't excluded, and could count toward EV-charging surplus undetected — the opposite of the intent above. Fixed by adding `outBatteryDataValid` to `GridDataSourceReadFn` (`grid_data_source.h`): the Sungrow source tracks `lastBatteryReadOkMs`/`batteryEverReadOk` and reports valid only within `STALE_DATA_TIMEOUT_MS` of a real successful+sanity-passing read (which since 2026-09-06 also requires `13000` to have yielded an unambiguous charge/discharge direction — see the register notes above); every simulated source reports `true` unconditionally ("no battery" is itself a known, trustworthy state). `compute_next_target_amps()` takes this as a new parameter and clamps `deltaA` to non-positive whenever it's false — the EV target can still hold or decrease on unverified data (always safe), but never increase, so a brief telemetry blip can't silently open a window for the car to draw on battery discharge. Deliberately asymmetric/"freeze, don't ramp-down" rather than forcing an immediate drop to the floor, so a routine few-second Modbus hiccup doesn't visibly interrupt an in-progress charge. Surfaced as `status.battery_data_valid`/JSON `battery_data_valid`/the control page's `batteryStaleNote`, independent of the existing grid-staleness `MODE_BYPASS` path (which is keyed only to the grid-power register and pulls in the opposite direction — full native pass-through — so is left untouched). This does not shrink the inherent poll + settling reaction latency to a real, *measured* discharge event (documented above as accepted elsewhere in the control loop) — it only closes the separate "unmeasured discharge" gap. Since 2026-09-06 the clamp is an **AND across the whole averaging window** rather than a per-sample check, so a single untrusted reading forbids an averaged increase — see "Control-loop damping".
- **All simulated sources are reactive** (`outWatts = currentDrawW + houseLoadW - pvCapacityW`), so reported export shrinks as target amps rises and the loop visibly converges instead of climbing to max (constant-value sources didn't do this — see "Resolved"). One file per scenario: `_no_sun` (0W PV, never charges), `_low` (2200W PV, nets just under the 6A/1,440W floor), `_moderate` (4000W PV, ~13.3A), `_high` (9000W PV, exceeds `MAX_CURRENT_A`), `_battery_discharge` (0W PV/800W load/7400W simulated discharge — `outWatts` alone looks like ~27A surplus, but `outBatteryW` correctly keeps target amps pinned near the floor). This is what "simulation mode" reduces to — picked from the same control-page dropdown as a real source.
- **`_lagged_cloudy` is the one simulated source that isn't instantaneous**, and the only one that can reproduce the control loop's oscillation (`grid_source_simulated_lagged_cloudy.cpp`, 2026-09-06). The five sources above reflect `currentDrawW` back **perfectly and noise-free**, which is exactly the case a gain-1 deadbeat law is unconditionally stable against — that is precisely why the ring never showed up on the bench despite the family being otherwise faithful. This one adds the two things reality has: a **vehicle ramp** (rate-limits an internal draw toward `currentDrawW` at 480W/s ≈ 2A/s, advanced on `millis()` deltas so it stays honest if `POLL_INTERVAL_MS` changes) and a **transport delay** (a 2-poll FIFO ≈ 10s, modelling the meter→RS485→register chain), plus deterministic cloud variation (two incommensurate sines, ~17s and ~6.3s, **never `random()`** — a run before and after a change must be comparable). PV base 3800W/house 800W puts supportable current in a 5-20A band, which also covers 6-8.6A, a range no other source lands in (see the entry-gain trap under "Control-loop damping"). It also flaps `outBatteryDataValid` false for 2 polls in every 24 — no other source ever reports `false`, so without it the "an averaged increase must not sneak past an unverified battery reading" rule has no test at all. Kept rare deliberately: frequent enough to observe in a few minutes, too rare to distort the oscillation being reproduced.
- **Grid voltage is per-source**, not a global setting: `GRID_SOURCE_SUNGROW_WINET` reads register `5018`; a failed read falls back to the last good value (or `MAINS_VOLTAGE_FIXED_V`) since voltage only affects amps↔watts precision, never safety. Simulated sources report a fixed `MAINS_VOLTAGE_FIXED_V` (240V, `config.h`). `solar_control.cpp` caches the last reported value (`s_last_mains_voltage_v`) for status display only.

## Control-loop damping

Added 2026-09-06, replacing the single `SETTLE_MS` window. The old law was
`deltaA = surplusW / V` applied at **gain exactly 1**, with no filtering anywhere between
the Modbus read and the commanded amps.

- **Why gain 1 rings.** Let `S` be the true supportable current, `t_n` the target after
  decision *n*, `e_n = t_n - S`. If the reading has fully absorbed the last correction,
  `t_{n+1} = t_n + (S - t_n) = S` — deadbeat in one step, which is what the law was designed
  for and is correct. With **exactly one decision-period of unabsorbed lag**,
  `e_{n+1} = e_n - e_{n-1}`, characteristic `z² - z + 1 = 0`, roots `e^{±iπ/3}` — magnitude
  **exactly 1**. The error neither grows nor decays: an undamped ring with a period of six
  decisions. So one step of lag is not "a bit marginal", it is precisely the stability
  boundary, and everything real pushes past it (the DTSU666→RS485→register cadence, the
  vehicle's own current ramp, and the poll being up to `POLL_INTERVAL_MS` stale at decision
  time). Reported by the user as the charge current oscillating, worst on cloudy days.
- **Why a gain and not the per-step cap that was removed earlier.** With gain `g`,
  `e_{n+1} = e_n - g·e_{n-1}` gives poles of magnitude `√g` — stable for any `g < 1`. The law
  stays an **integrator**, so steady-state error is still exactly zero and a large error still
  produces a large step; `g` damps only the transient. A per-step cap is a fixed rate limit
  that bites just as hard when the plant is fully settled. These are not the same thing, and
  reintroducing the cap is not what happened here.
- **Blanking, then averaging.** Each accepted change starts a **blanking** window
  (`blank_ms`, default 10s) whose readings are **discarded, not averaged in** — they still
  show the plant's *previous* operating point, so folding them into a mean biases it toward
  the pre-ramp, apparently-larger surplus and makes the oscillation *worse*. This is the
  trap: naive smoothing across the whole window is an anti-fix. After blanking, the next
  `avg_samples` (default 3) successful readings are averaged and one decision is made on the
  mean. During that phase the target is constant, so every sample measures the same operating
  point and the mean is unbiased. Averaging is gated on a **sample count, not elapsed time** —
  a time window overlapping two failed Modbus polls would decide on one sample or none, which
  is the aliasing being removed; a dropped poll just stretches the wall clock. The accumulator
  resets after **every** decision, changed or not, or a deadbanded no-change would leave the
  window expired and let the next single sample decide alone.
- **Gain is asymmetric, and never applied at entry.** `gain_up` (default 0.7) scales
  *increases* only; decreases keep full gain, since down is always the safe direction and is
  what stops grid import. It is applied **only while `currentTargetA >= MIN_CURRENT_A`**: at
  target 0 the EV contributes nothing to the meter, so the reading is the true supportable
  current rather than an error term carrying our own lag. Damping it would move the effective
  entry threshold from 6A to `MIN_CURRENT_A/gain_up` = 8.6A and silently undo the documented
  "entry is decided directly against the floor's wattage, no margin" behavior — charging would
  simply never start in that band. **No existing simulated source lands between 6A and 8.6A**,
  which is why `_lagged_cloudy` is deliberately scaled to cover it.
- **The `!batteryDataValid` clamp is an AND across the window**, not a check of the newest
  sample, and stays **last** — after the gain — so it is unconditionally final. One untrusted
  reading anywhere in the window forbids an averaged increase; otherwise smoothing walks
  straight past the guard added 2026-09-05.
- **Deadband** (`deadband_a`, default 0.5A) suppresses a decision that would move the target
  less than that: no change, and no restarted blanking window. Applied *after* the
  floor/hysteresis banding, so it can never suppress a floor crossing (those move by at least
  `MIN_CURRENT_A`). Sized above the ~0.3A (`MIN_CLAMP_MARGIN_PCT` × 0.6 A/%) that
  `cp_interceptor.cpp` refuses to re-arm the clamp for, so every accepted change is one the
  hardware actually applies — previously a 0.05A nudge that changed nothing physically still
  cost a full settle window of responsiveness.
- **Fast-drop path**: a single reading showing import ≥ `fast_drop_a` (default 2.0A ≈ 480W)
  cuts at full gain immediately, bypassing both windows, so averaging only ever delays
  *increases*. Two gates it must keep: (1) **`currentTargetA > 0`** — there is nothing to cut
  at 0A, and an evening's house load alone (800W = 3.3A) would otherwise fire it every poll
  and starve the averaging window forever; (2) **suppressed during the blanking window that
  follows a *down* change, armed after an *up* change**. That asymmetry falls out of the lag
  sign: after an up change the un-ramped car makes the meter read *more export* than reality,
  so an import reading *understates* the deficit and a full-gain cut is an under-cut (safe);
  after a down change the residual import **is our own previous cut, not yet absorbed**, and
  acting on it is the exact double-count being fixed — it would cut through the floor and open
  the CP disconnect relay. Net: the fast path can fire at most once per `blank_ms`, still
  faster than the old 15s `SETTLE_MS`.
- **Cadence trade.** Up-direction decisions go from 15s to ~25s (10s blank + 3 × 5s poll), and
  a large surplus jump is ~97% captured in 3 decisions (~75s) rather than one poll. Down gets
  *faster*. Entry from 0A is undamped and still lands in one decision.
- **All five values are runtime-tunable** from the control page (`/api/set_tuning`), persisted
  in their own `"control"` NVS namespace (independent of `netcfg`/`gridsrc`/`schedule`), and
  `constrain()`ed on **both** load and set so neither a corrupt NVS blob nor a hand-crafted
  query arg can put the loop outside its stable range (`gain_up` is capped at 1.0). They are
  tunable rather than compiled in because the right values depend on this install's actual
  inverter and vehicle lag, which can only be measured against real weather. `config.h` holds
  the defaults only. **If ringing persists, tune in this order**: `blank_ms` up first (a
  too-short blank is the failure mode averaging cannot fix), then `gain_up` down to 0.5, then
  `avg_samples` up.
- `blank_ms` is the one guessed number — the vehicle's ramp rate is still unmeasured on this
  install. To measure it: force a 6A→16A step via a schedule window and watch `grid_w` on the
  page's 5s poll until it flattens; set `blank_ms` to ~1.5× that.
- Control state (`ControlLoopState`: blanking timestamp, direction of the last change, the
  accumulator, and the battery-validity AND) is a `solar_control_task` **local passed by
  reference**, not a file-scope static — the law stays a function of its arguments, and the
  schedule-override path resets it explicitly. `handle_api_set_source()` and
  `handle_api_set_tuning()` set `s_control_reset_requested` so a half-full accumulator never
  spans two different plants or outlives a shrunk `avg_samples`.
- **Instrument with the serial trace or `/api/status`, never the history chart** — its
  5-minute buckets average a 30s oscillation into a flat line. `solar_control.cpp` logs one
  `control:` line per decision (grid/effective watts, battery validity, sample progress,
  old→new amps, reason); it is the only per-poll trace in the file.

## Hardware: single ESP32-S3

Board: Freenove ESP32-S3-WROOM on its breakout board — its screw-terminal rails (3V3/5V/GND) power the whole CP interceptor circuit too, hence the shared-ground design (see "CP interception circuit"). Dual-core split:

- **Core 0**: WiFi + Modbus TCP poll loop; computes target current from surplus. `compute_next_target_amps()` (`solar_control.cpp`) is a damped, averaged integrator, bounded by `MIN_CURRENT_A`/`MAX_CURRENT_A` — see "Control-loop damping" below for the full scheme and the stability argument behind it. There is still **no per-step rate cap**: a decision moves the target as far as the error warrants. Below the 6A floor (no current yet to self-correct against), entry is decided directly against the floor's wattage, no margin **and no damping** — a cold start with abundant surplus still reaches equilibrium in a single decision; exit uses `HYSTERESIS_A` to avoid flapping (mirrors `cp_interceptor.cpp`'s own thresholds). Also owns the BLE config server.
- **Core 1** (pinned, high priority): real-time CP interception.
  - Edge timestamping is a plain GPIO `ANYEDGE` interrupt (`esp_timer_get_time()` in the ISR) — not RMT RX, which is built for after-the-fact burst capture, not low-latency reaction to the current edge.
  - Pre-assert delay uses the legacy hardware timer group API (`driver/timer.h`): a free-running 1MHz timer armed directly from `cp_sense_isr()` (interrupt context, zero task hop). On fire, `assert_timer_isr()` (also interrupt context) asserts the clamp by writing the RMT item directly into hardware via register-level `rmt_ll_*` calls (`rmt_ll_tx_reset_pointer`/`rmt_ll_write_memory`/`rmt_ll_tx_start`) — mirroring what `rmt_write_items()` does, but IRAM/ISR-safe, since `rmt_write_items()` itself is flash-resident and can't be called from this ISR; RMT's idle-low guarantees release even if the task stalls, and release rides the EVSE's own falling edge.
  - `cp_interceptor_task` only plans, on its own cadence (`CP_NOTIFY_WAIT_MS`): floating-point duty%/offset math producing integer tick counts the ISR applies on the next rising edge, via Core-1-local `volatile`s (ticks written before dutyState so the ISR can never see `CP_OSCILLATING` paired with stale params). This is deliberately the only floating point in the path — **never in the ISR**, since the Xtensa FreeRTOS port saves/restores the FPU lazily per task and that isn't guaranteed safe on arbitrary interrupt entry/exit (confirmed via `portmacro.h`'s `coproc_area`; no `FPU_IN_ISR` Kconfig option exists to check instead).
  - Superseded three earlier approaches (kept here so they aren't retried): encoding the delay in the RMT item itself (re-arming every ~1ms caused significant jitter); a software `esp_timer` for the delay (real dispatch jitter — no ISR dispatch or core pinning in this build); routing the decision through a queue to the task instead of arming straight from the ISR (ordinary task-dispatch latency on top).
  - **Native duty is learned opportunistically, not measured live while clamping** — once clamping every cycle, the sense point can't distinguish the EVSE's real falling edge from the clamp's own assert transition, so the cached native-high-duration only updates on cycles the clamp didn't fire (`STANDBY`/`BYPASS`/target≥native). Clamping is skipped until native duty has been learned once (fails toward pass-through).
  - Reads target amps from Core 0 via a FreeRTOS queue/mutex, not a raw shared variable.
  - Toolchain: `platform = espressif32@6.10.0` → Arduino-ESP32 core 2.0.17/ESP-IDF 4.4, so RMT means the **legacy** `driver/rmt.h` API, not IDF5's `driver/rmt_tx.h`/`rmt_rx.h` channel API.

### GPIO constraints

- Avoid strapping pins for CP sense/drive lines.
- **Pin assignments (`include/config.h`, physically confirmed on the bench):**
  | Signal | GPIO | Notes |
  |---|---|---|
  | CP PWM sense / EDGE_IN (digital, post-opto) | 5 | `ANYEDGE` GPIO interrupt + timestamping |
  | Clamp drive (RMT TX → opto → MOSFET gate driver) | 6 | |
  | CP connector-state sense / CONNECTED_IN (digital, post-opto) | 4 | polled, no interrupt; level discrimination happens in hardware, not via ADC |
  | CP disconnect relay drive (opto → relay coil driver) | 7 | plain digital output, task-context only |

  GPIO 8/9 (formerly the status LCD's I2C bus) are unused now that the LCD has been removed.

## BLE configuration

- WiFi SSID/password, the inverter IP, and two independent passwords (BLE-config gate, HTTP control-page gate) have **no compile-time fallback** — `secrets.h` holds only `OTA_PASSWORD` (OTA flashing only). Everything else is provisioned at runtime over BLE (`src/ble_config.*`), persisted to NVS (`Preferences`, namespace `netcfg`), read via `shared_state`'s `RuntimeConfig`.
- **Owned by Core 0 only, never Core 1** — BLE isn't real-time, and a stuck/disconnected client must never affect the control loop or fail-safes. Uses `NimBLE-Arduino` 1.x (much lower footprint than the Arduino core's legacy `BLEDevice.h`; NimBLE 2.x targets IDF5, which would conflict with Core 1's legacy `driver/rmt.h`).
- `ble_config_init()` runs once from `setup()`, independent of WiFi/`solar_control_task` state, so BLE comes up even on a fully unprovisioned board. A separate `ble_periodic_task` re-evaluates the advertising window every ~1s.
- **Transport: Nordic UART Service (NUS)**, not a custom multi-characteristic GATT profile — ordinary BLE serial-terminal apps auto-detect NUS but can't drive a custom profile field-by-field (caught bench-side as a real connection failure against Serial Bluetooth Terminal). One RX (`WRITE`/`WRITE_NR`) + one TX (`NOTIFY`) characteristic (`6E400001`/`6E400002`/`6E400003-B5A3-F393-E0A9-E50E24DCCA9E`), newline-delimited text commands. `NimBLEDevice::setMTU(247)` requested up front so multi-line replies don't truncate before negotiation completes.
- **Command protocol** (`RxCallbacks::onWrite` assembles lines on `\n`, tolerating a trailing `\r`, dispatched via `process_line()`); `SET <FIELD> <value>` / `GET <FIELD>`, each password field named for what it gates:
  | Command | Auth required | Behavior |
  |---|---|---|
  | `AUTH <password>` | no | Compares to `RuntimeConfig.ble_password`. Unset (factory-fresh) authenticates unconditionally. Sets/clears a global authenticated flag (reset per connection) gating every `SET`/`COMMIT` below. |
  | `SET WIFI_SSID <ssid>` | yes | Stages a new SSID (not yet persisted). |
  | `SET WIFI_PASS <password>` | yes | Stages a new WiFi password. |
  | `SET INVERTER_IP <ip>` | yes | Stages a new inverter IP; rejects anything that doesn't parse via `IPAddress::fromString()`. |
  | `COMMIT` | yes | Atomically persists + publishes the three staged WiFi/inverter fields via `shared_state_set_wifi_config()` (bumps `generation`), so `solar_control_task` never observes a half-updated config. |
  | `SET BLE_PASS <password>` | yes | Sets the `AUTH` password. Applies immediately, doesn't bump `generation`. |
  | `SET WEB_PASS <password>` | yes | Sets the HTTP control-page password. Same immediate-apply pattern. |
  | `GET STATUS` | no | Reports SSID, staged inverter IP, live device IP, provisioned/auth flags, whether `BLE_PASS`/`WEB_PASS` have ever been set — **never echoes a password**. |
  | `HELP` | no | Lists the commands above. |
  | unrecognized `SET`/`GET` field, or unrecognized command | — | `ERR unknown field, try HELP` / `ERR unknown command, try HELP` |
- **Advertising window**: `BLE_ADVERTISE_WINDOW_MS` after boot, **except** indefinitely while never provisioned (BLE is the only config path). Re-evaluated ~1s by `ble_periodic_task`; doesn't drop an already-open connection.
- **Core 0 apply flow**: `connect_wifi()` skips `WiFi.begin()` entirely if unprovisioned/empty. `solar_control_task` tracks the last-applied `generation` and reconnects on change — only `COMMIT` bumps it, `SET BLE_PASS`/`SET WEB_PASS` never trigger a WiFi bounce. Unprovisioned/WiFi-less is already safe without new logic: Core 1's stale-data fail-safe already treats it as native pass-through.

## CP interception circuit

See `schematic/schematic.png` (source: `schematic/solar-ev-charge-controller/`) for the actual schematic — this section is the rationale behind it, not a restatement of every value; reference designators (`R5`, `U2`, `Q2`, etc.) match that drawing and were re-confirmed pin-by-pin after a later KiCad renumbering pass.

- **Reference**: CP (and PP) reference PE, not a floating signal ground or neutral. Confirm PE continuity before tapping in.
- **Isolation is signal-only, not power-domain**: `EDGE_IN`/`CONNECTED_IN`/`CLAMP_DRIVE` each cross into the ESP32's domain via their own optocoupler (`U3`/`U4`/`U1`, SFH617A-3). The sense divider, both comparators, and the clamp MOSFET (`Q2`) share `GND`/`+5V` with the ESP32 side — no separate PE-only rail. CP-side fault protection comes from the high-Z sense divider (`R5` 100kΩ) and `D3`/`D4` clamp diodes, not full galvanic isolation (deliberate — see [Open questions](#open-questions-for-implementation)).
- **Sensing**: `R5`(100k)/`R6`(33k) divider brings the CP swing down to a `SENSE` node, compared by an LM393 (`U2`) against a ladder (`R8`/`R9`/`R10`): REF_CONN≈2.5V (unit 1) → `CONNECTED_IN` via `U3`; REF_EDGE≈0.45V (unit 2) → `EDGE_IN` via `U4`. Two thresholds on one node give four buckets — A / B / C(+D) / FAULT(=E+F) — not full six-level discrimination; accepted since D (ventilated charging) is unused on this install and E/F both already mean "don't clamp."
- **Sensing values** (hand-verified 2026-08-30): REF_CONN 2.500V / REF_EDGE 0.450V at nominal, correctly bracketing their state boundaries after the 0.2481 divider ratio. At ±5% resistor tolerance, REF_CONN's worst case would overlap state-B's worst case by ~31mV, so `R5`/`R6`/`R8` are specified at 1% (others stay 5%) to close that gap. Confirmed landing correctly against the real EVSE in stage 2.
- **Clamping**: not a regenerator, and not a series break — `CP_LINE` runs continuous and uncut. `Q2` (2N7000) taps on through a series blocking diode (`D2`) and shunts toward `GND` when driven, only during the high portion of an in-progress cycle; `D2` isolates the negative half-cycle and `Q2`'s own body diode from the tap. `Q2`'s gate defaults off via a 10k pull-down (`R3`) — no relay in this leg (a weaker guarantee than a relay: a shorted `Q2`/opto could hold the line low continuously, but that's still non-hazardous — reads as a fault to the EVSE).
- **Disconnect relay (`K1`)**: NC, energize-to-open, in series on `CP_LINE` downstream of the sense/clamp tap. Own optocoupler + low-side driver (`Q1`, 2N7000) + flyback diode (`D1`). De-energized = closed = pass-through (same fail-safe direction as `R3`/`Q2`). Only `CP_STANDBY` energizes it, isolating the vehicle's CP termination — indistinguishable from a real unplug to the EVSE; reclosing renegotiates the handshake (A→B→C) like a fresh plug-in.
- **Inherent fail-safes**: no `CLAMP_DRIVE` (idle/unpowered/pre-firmware/watchdog reset) → `R3` holds `Q2` off → native pass-through, unconditionally. `Q2` stuck on/shorted → EVSE reads a fault/disconnect, stops offering charge. Clamp can only pull toward `GND`, never raise duty above native, regardless of firmware state. No relay-coil drive → NC stays closed → pass-through — losing the ESP32 must never leave the vehicle unable to charge.
- **Explicit fail-safes**: stale-data timeout (~60s, `STALE_DATA_TIMEOUT_MS`) → `MODE_BYPASS`, stops clamp scheduling, keeps the relay closed regardless of duty state — charging proceeds native/uncapped until the fault clears (deliberate: a data fault never triggers a disconnect). Hardware watchdog on the CP task forces reboot on a hang; RMT defaults idle-low on reset. Power loss → both optos stop driving, `R3` and the de-energized relay both fail to pass-through. Relay dwell-time debounce (`RELAY_MIN_DWELL_MS`, on top of the amps hysteresis) bounds relay cycling and gives the handshake time to complete before another flip.

## Firmware implementation

PlatformIO project, `env:freenove_esp32_s3_wroom`, framework `arduino`. Builds clean (`pio run`, zero warnings). Layout:

- `include/config.h` — pins, control-loop constants, thresholds. Anything still marked TBD here maps 1:1 to an item in "Open questions" below.
- `include/secrets.h` (gitignored) — just `OTA_PASSWORD`, used solely for OTA flashing. Auto-generated from `.env` by `tools/sync_secrets.py` (a PlatformIO pre-build step) — edit `.env`, not this file. WiFi credentials, the inverter IP, and the BLE-config/control-page passwords are never compiled in — see "BLE configuration" above.
- `include/build_info.h` / `src/build_info.cpp` — `firmware_build_id()`, the running firmware's build stamp (`"2026-09-06 03:07:47 UTC (117c73b-dirty)"`). The stamp itself lives in `include/build_info_stamp.h`, gitignored and regenerated on **every** build by `tools/sync_build_info.py` (a second PlatformIO pre-build step alongside `sync_secrets.py`; UTC timestamp plus a best-effort `git rev-parse --short HEAD`, `-dirty` when the tree is). `build_info.cpp` is the only TU that includes the generated header, so the per-build churn costs one small recompile plus a relink, not a full rebuild — keep it that way. Consumed by the control page's auto-refresh, below.
- `src/shared_state.*` — the Core0↔Core1 bridge: an `xQueueOverwrite` queue (length 1) for target-amps, plus a mutex-protected status struct each direction. Core 1's side always uses zero-timeout takes so a contended mutex can never stall the real-time task. Also holds the BLE-provisioned `RuntimeConfig`.
- `src/modbus_tcp_client.*` — hand-rolled minimal Modbus TCP client: one persistent connection reused across polls, reconnecting only on failure (write error, timeout, malformed response) — never more than one open at a time. `setHost()` drops and reconnects on IP change. Generic, no register-map knowledge.
- `src/grid_data_source.h` — the `GridDataSource` interface. `src/grid_data_source_registry.cpp` — compiled-in source list + id lookup. `src/grid_source_sungrow_winet.cpp` — the real Sungrow WiNet-S/SH8.0RS implementation. `src/grid_source_simulated_reactive_{no_sun,low,moderate,high,battery_discharge}.cpp` — the reactive simulated family, one file per scenario, each also a minimal reference for adding a real second source. `src/grid_source_simulated_lagged_cloudy.cpp` — the lag/noise model, the only source that reproduces the control-loop oscillation and therefore the regression test for the damping. See "Solar data source" above.
- `src/solar_control.*` — Core 0: WiFi connect/reconnect (from `RuntimeConfig`), poll loop, control law, OTA, HTTP control page.
- `src/ble_config.*` — Core 0: BLE provisioning server (WiFi/inverter-IP config, BLE-config/control-page passwords, current-IP readback).
- `src/cp_interceptor.*` — Core 1: GPIO-interrupt edge capture, RMT clamp waveform, disconnect relay drive, `BYPASS`/`ACTIVE` × `OSCILLATING`/`STANDBY` state machine, task watchdog.
- `tools/probe_sungrow.py` — host-side diagnostic, not part of the build: dumps and decodes the inverter's battery/grid register block (`13000`, `13009`-`13010`, `13019`-`13022`, `5213`) so a mapping can be correlated against the Sungrow app directly. Stdlib-only, and deliberately mirrors `modbus_tcp_client.cpp`'s FC4 and word handling so it sees exactly what the firmware sees. Run it before changing any register mapping — guessing is what produced the `13021` saga in "Resolved". Note the WiNet-S generally allows only one Modbus TCP client at a time, so the ESP32 may need powering down while probing.

### OTA & the HTTP control page

- **OTA**: `ArduinoOTA` starts once WiFi connects, password-protected via `OTA_PASSWORD`. Core 0 blocks on flash writes, so the poll loop pauses; a push longer than `STALE_DATA_TIMEOUT_MS` (60s) triggers Core 1's stale-data bypass mid-update — expected, not a fault to avoid.
- **Bench/night-time testing**: no separate "simulation mode" — the reactive simulated sources are picked from the same control-page grid-source dropdown as any real source, exercising the full poll/control-law/target-amps path (though stale-data fail-safe testing still needs real hardware, since a simulated source always succeeds).
- **Control page**: `http://<device-ip>/`, HTTP Basic Auth (`admin` / `RuntimeConfig.web_password`, set via `SET WEB_PASS`, never `OTA_PASSWORD`). Refuses every request with 403 until a password has been committed at least once — no "open until first set" grace period, unlike WiFi, since this is network-reachable rather than a physical jumper. The interceptor's hardware topology already bounds what bad data here can do (clip down or fall back to native, never raise above native).
- **The page keeps itself current across a reflash** (2026-09-06). Two halves, both required. (1) Every handler calls `send_no_cache_headers()` before its `send*()` — Arduino `WebServer`'s `_prepareHeader` emits only the status line, `Content-Type`, `Content-Length` and `Connection`, so with no `Cache-Control` at all browsers fell back to heuristic freshness and could serve a cached `PAGE_HTML` indefinitely after an OTA: old JS silently driving a new `/api/status`. `_responseHeaders` is consumed and cleared per response, so this must be per-handler, never once at setup. (2) `/api/status` carries `build_id` (`firmware_build_id()`); the page captures the first value it sees into `seenBuildId` and calls `location.reload()` from the top of `render()` when a later poll disagrees, so the existing 5s poll is the whole trigger — no new timer. Half (1) is also what makes (2) terminate: a reload handed the same cached shell would loop forever. A plain reboot leaves the stamp unchanged and correctly does **not** reload. The stamp also renders in the page footer (`#buildInfo`, deliberately outside `#dashboard` so `showError()` doesn't hide it).
- **Don't reach for a runtime image hash instead** — both obvious candidates are dead ends here, checked 2026-09-06. `esp_ota_get_app_description()->app_elf_sha256` is all zeros, because PlatformIO's Arduino-framework `ElfToBin` builder never passes `--elf-sha256-offset` to esptool (only its ESP-IDF path, `builder/frameworks/espidf.py`, does), and that struct's `date`/`time` come from arduino-esp32's *precompiled* `esp_app_desc.c`, so they're identical across our builds. `ESP.getSketchMD5()` does genuinely hash the flashed image, but costs a ~1.2MB flash read and yields only opaque hex — no use for the visible footer.
- `s_json_body` is sized **3072**, against a computed worst case of **2048** bytes (longest `decision`/`cp_mode_title`/`cp_duty_title`/`connector_title` strings, longest source name, all **7** registry entries, `build_id`, the `avg_n`/`avg_of` averaging progress and the five `tune_*` values). The previous 2048 was worst-case-exact *before* the NUL, so the damping work would have truncated it; 1792 before that left ~18 bytes. Re-check this arithmetic before adding another field or another grid source — `build_status_json()` truncates silently, and truncated JSON blanks the page exactly like the `nan` bucket did. Keep every `decision_reason_str()` string ≤57 chars (the `SCHEDULE_OVERRIDE` line), which is what the accounting assumes.
- **Power history chart**: a device-side ring of 5-minute buckets (`s_history`, averaged on read by `build_history_json()`), persisted to LittleFS so it survives reboots, served from `/api/history` and drawn client-side. Only real readings are recorded (`timeSynced && modbus_ok`), so an outage reads as an honest time gap rather than a dip to zero. **Invariant: never emit or persist a zero-sample bucket** — `target_sum_w / sample_count` is then `0.0f / 0` = NaN, and `printf("%.0f")` renders that as `nan`, which is *not* valid JSON, so one such bucket makes the browser's `JSON.parse()` throw and blanks the entire chart. See "Resolved".

Bench-tested through all three stages — real EVSE + real vehicle confirmed working 2026-09-04. Real EVSE is a Geely-branded Jueclat EV Charger-Lite, model WB-AC230-7-N-C-W/S-EU2.0 (single-phase 230V, 7kW, matching the "no API/Modbus/WiFi control path" assumption above).

## Open questions for implementation

All previously open items are now resolved.

- Shared-ground/signal-only isolation (see "CP interception circuit" above) — **kept as final, 2026-09-04**, not a galvanically-isolated PE-side supply. Not worth the added cost/complexity given the existing protection (high-Z `R5` divider + `D3`/`D4` clamp diodes).
- Battery-power register (`13021`) exact scale — **closed out, 2026-09-04**. The ~10% discrepancy against the Sungrow app is attributed to correlation-window skew on a cloudy/fluctuating sampling day, not a real register/scale error.
- BLE range/reliability inside the metal EVSE enclosure — confirmed adequate, no external antenna needed.
- Resistor divider/comparator thresholds — confirmed against the real EVSE in stage 2; 1% tolerance on `R5`/`R6`/`R8` is sufficient.
- GPIO pin assignments — physically wired and confirmed correct in stages 0-2.
- Whether the vehicle accepts live CP duty-cycle changes mid-charge — **confirmed yes, 2026-09-04**, no state-B blip needed.
- Settling period (`SETTLE_MS`), hysteresis band (`HYSTERESIS_A`), relay dwell time (`RELAY_MIN_DWELL_MS`), and clamp dispatch-latency compensation (`CLAMP_DISPATCH_LATENCY_US`) — confirmed adequate at their current values against the real vehicle, 2026-09-04. **`SETTLE_MS` has since been superseded** (2026-09-06) and that "adequate" needs qualifying: it was confirmed adequate for the *vehicle accepting live duty changes*, which is all stage 3 tested. It was never adequate against total **measurement** lag, and at gain 1 it could not have been — see "Control-loop damping". The other three stand.
- Battery-power register (`13021`) mapping corrected, 2026-09-04 — it's a standalone single register, not the low half of a `13021`-`13022` S32 pair (that assumption gave an obviously-garbage 58M W reading). Confirmed via a standalone script against real battery discharge; ±20kW sanity bound kept regardless. (The same entry also called it an S16 and negated it; that half was wrong — see the two entries below.)
- Battery-power register (`13021`) sign convention flip-flopped twice on 2026-09-05, both times wrong — **kept here because the shape of the mistake is the lesson, not the conclusion.** Attempt 1 dropped the negation (inferred from a `grid_w:9495`/`battery_w:6400`/`battery_state:"discharging"` control-page pull during a grid-scheduled battery charge); attempt 2 restored it the same day, after a directly Sungrow-app-confirmed discharge then showed as `"charging"` — read at the time as "clear evidence the raw register is positive=discharging." Both attempts assumed the register carried *a* sign and argued about which one; each looked right against whichever direction was checked and wrong against the other, so each observation was read as proof of the opposite convention. The register has no sign at all — see the next entry. Two lessons the codebase should keep: an indirect inference ("a 9.5kW import spike is consistent with charging") is not a reading, and a hypothesis that only ever gets tested in one direction isn't tested.
- Battery-power register (`13021`) is **magnitude-only; direction lives in register `13000`** — root-caused and fixed 2026-09-06, superseding both entries above and closing the "a real charging event has never been directly confirmed" item they left open. Reported by the user: during the 12am-6am cheap-tariff window, when the home battery charges *from the grid*, the control page said **discharging**; during a genuine discharge into house loads it also said discharging. That asymmetry is the tell — the page was reporting "discharging" unconditionally, and had simply been checked against a real discharge every previous time. Every observation on record (2026-09-04 discharge, 2026-09-05 grid charge, 2026-09-05 discharge, 2026-09-05 overnight grid charge) is consistent with "raw `13021` is always positive", and no single-register sign convention can satisfy all four. Cross-confirmed by mkaiser's Sungrow register notes ("old firmware (before october 2024): always positive battery power"), evcc's Sungrow template (reads `13021`, then sign-corrects from `13000`), and a third community register map. Fixed by taking the magnitude from `13021` and the direction from `13000`'s bits 1/2 — see "Solar data source" above. **Directly confirmed on this hardware the same day**, via one `tools/probe_sungrow.py` capture spanning a live discharge→charge transition (12:29:42→12:29:47): `13021` read +2654W decaying to 0 while discharging, then +419W rising to +1794W while charging — **positive throughout, never negative** — while `13000` flipped `0x001D`→`0x001B` (bit 2 `0x04` clearing, bit 1 `0x02` setting) exactly at the changeover. Both directions in one continuous log, which is the half every previous attempt was missing. Shipped firmware then verified on-device the same day: OTA-flashed, and the control page's Battery row tracked a deliberately-induced charge and discharge correctly in both directions. **Not just a display bug**: `effectiveGridPowerW = gridPowerW + fmaxf(0, -batteryPowerW)` was adding the battery's *charge* power back as though it were discharge, so with e.g. 2kW export and the battery charging at 3kW the loop computed 1kW of apparent *import* and suppressed EV charging the sun was actually supporting — it stole real surplus from the car whenever the battery charged. `tools/probe_sungrow.py` (new, stdlib-only, mirrors `modbus_tcp_client.cpp`'s FC4 exactly) exists so this register block can be dumped and correlated against the Sungrow app directly instead of inferred; use it before touching any register mapping again.
- Unmeasured battery discharge could silently leak into EV-charging surplus, fixed 2026-09-05 — same day as the sign-convention fix above, prompted by the realization that with no way to separately meter house vs. EV load, the battery-discharge exclusion (2026-09-04, "Solar data source" above) is only as trustworthy as the battery reading behind it, and a failed/rejected/never-yet-obtained reading silently defaulted to `0.0f` ("idle"), so a real discharge that wasn't currently being measured wasn't excluded. See "Solar data source" above (`outBatteryDataValid`) for the fix — the control law now only ever holds or decreases the EV target on unverified battery data, never increases it.
- Power history chart went permanently blank after any reboot, fixed 2026-09-06 — `history_save_to_fs()` was called immediately after a new bucket was created and *before* its first sample was added, so the persisted file's newest bucket always held `sample_count == 0`. A reboot restored that bucket, its 5-minute window had already passed so it could never be filled, and `build_history_json()` then divided by zero and emitted `"target_w":nan` — not valid JSON, so `JSON.parse()` threw in the browser and the chart drew nothing, permanently. Compounded by an empty `.catch(function(){})` on the `fetch`, which swallowed the parse error and left nothing in the console to diagnose. Fixed three ways: persist only *after* the first sample lands, skip zero-sample buckets when building the JSON (which also repairs an already-persisted bad file, and reads as an honest gap), and log the reason in that catch instead of discarding it. Surfaced by the user right after an OTA reboot; the offending bucket was timestamped to the exact minute the board was powered down for Modbus probing.
- Relay-based CP disconnect/reconnect is clean and recoverable — confirmed via a manual CP-wire disconnect while charging and via bench validation of the actual `K1` circuit in stages 1-2.
- Both CP sense GPIOs' idle-level polarity was inverted from the original assumption (`CP_CONNECTED_SENSE_GPIO` LOW=state A; `CP_PWM_SENSE_GPIO` LOW=CP high) — this had caused clamping to land in the negative half-cycle; fixed along with a related bug where hold-duration double-counted `CLAMP_DISPATCH_LATENCY_US`.
- `CP_STANDBY` used to release the clamp to full native pass-through instead of stopping charging — backwards, since it happened exactly when surplus was lowest. Fixed by adding the disconnect relay (`CP_STANDBY` under `MODE_ACTIVE` now opens it; `MODE_BYPASS` is unaffected).
- `compute_next_target_amps()` used to ramp through fictitious sub-floor current, able to overshoot into a deficit at the 6A floor. Fixed by branching on whether currently charging: below-floor entry is decided directly against the floor's wattage each poll, no intermediate steps.
- All simulated grid sources used to be constant-value and never converged (didn't subtract the EV's own draw, so the loop always saw more headroom no matter how much current was already committed). Fixed by making sources reactive and removing the per-poll step cap entirely, relying on `SETTLE_MS` alone to gate reaction rate. **The second half of that was revised 2026-09-06**: a settle window alone is not enough, because it bounds *how often* the loop reacts without bounding *how far* — see the next entry. The per-step cap was **not** reinstated; the fix is a gain, which is a different thing (integrator, zero steady-state error).
- EVSE charge current oscillated, worst on cloudy days — root-caused and fixed 2026-09-06, reported by the user as "the data source measurements can lag behind what is actually happening". **The loop was sitting exactly on the stability boundary, not merely near it**: gain-1 deadbeat correction against a plant that answers late gives `e_{n+1} = e_n - e_{n-1}`, poles of magnitude exactly 1, an undamped six-decision ring. Compounded by there being no filtering of any kind in the whole chain — one instantaneous sample per ~15s window drove a full-magnitude jump, aliasing genuine cloud variance — and by any nonzero `deltaA` restarting the window, including a 0.05A nudge `cp_interceptor.cpp` would refuse to act on. Fixed with a blanking phase, a count-based averaging phase, an asymmetric gain, a deadband and a fast-drop path; see "Control-loop damping" for the whole scheme. **Three traps worth keeping**, each of which looks like the obvious implementation and is wrong: (1) averaging across the *whole* window is an anti-fix — the early samples still show the pre-ramp operating point and bias the mean *upward*, so blanking must discard rather than smooth; (2) applying the damping gain at target 0 silently moves the charging-entry threshold from 6A to `MIN_CURRENT_A/gain_up` = 8.6A, undoing the documented no-margin entry rule, because at 0A the reading is the true supportable current and not an error term; (3) an unconditional fast-drop path fires every poll on an ordinary evening's house load (800W = 3.3A) and starves the averaging window forever, and if left armed during the blanking window after a *downward* change it acts on its own not-yet-absorbed cut — through the floor and into a CP relay open.
- The reactive simulated family could never have caught the oscillation above, which is why it survived four clean bench stages — recorded 2026-09-06. Every one of those sources reflects `currentDrawW` back **instantaneously and noise-free**, which is precisely the `EV_actual = t_n·V` case a gain-1 deadbeat law is *unconditionally* stable against; running the buggy firmware against `_moderate` converges in one poll and sits there forever. A stability bug cannot be reproduced by a plant model with no lag in it. Fixed by adding `_lagged_cloudy` (see "Solar data source"), which models the vehicle ramp and the meter transport delay deterministically. **Reproduce before fixing**: flash the new source against the *unmodified* control law and confirm the ring first, otherwise the source is a rationalisation and a fixed loop is indistinguishable from a plant model that was never unstable.
- Entry to charging used to take two settled polls to reach true equilibrium (always snapped to exactly `MIN_CURRENT_A` first). Fixed by unifying entry and steady-state correction into one formula.
- Replaced the single fixed-scenario reactive source with a family spanning no-sun through more-sun-than-usable (`_no_sun`/`_low`/`_moderate`/`_high`), and removed the four constant-value sources and the manual global-voltage setting (each source now reports its own voltage).
